# Public Rename Impact Audit: tauri-plugin-stt to tauri-plugin-voice

## Scope

This audit covers externally visible references affected by renaming the plugin from STT to voice. It includes Rust package and crate naming, Tauri plugin namespace, commands, permissions, generated schemas, TypeScript package and imports, example app usage, docs, specs, and known local consumers.

It separates true API surface from internal-only implementation names. No source rename or consumer migration was performed in this task.

## Summary

The rename is a breaking public surface change unless compatibility aliases are intentionally kept. The current public contract is exposed through four layers:

- Rust crate metadata and Rust imports: `tauri-plugin-stt`, `tauri_plugin_stt`, `TauriPluginSttExt`.
- Tauri command namespace and permissions: `plugin:stt|...` and `stt:*`.
- TypeScript package and exports: `tauri-plugin-tauri-plugin-stt-api`, `bootstrapStt`, `sttHealth`, and related invoke wrappers.
- Consumer app configuration and generated schemas: example app and Steno both reference `stt:default` and Rust plugin symbols.

The highest migration risk is Steno. It depends on the Rust plugin crate directly and uses the extension trait for model downloads and transcription flow.

## Internal-Only Names

These names should not be treated as public API unless a consumer depends on repository source layout directly:

- `scripts/worker.py`
- `scripts/transcribe.py`
- `requirements/requirements-stt.lock.txt`
- Internal Rust method names inside `desktop.rs`, such as `download_model_inner` and `transcribe_file_internal`.
- Local comments that describe STT-only behavior.
- `SttWorker` and other private implementation types if they remain private.
- Existing historical spec folder names, unless they are active deliverables.
- Lock-file entries generated from package metadata; update through normal dependency regeneration rather than manual API design.

The lock file name `requirements-stt.lock.txt` is currently internal because it is consumed by the plugin bootstrap implementation, not by app consumers. It can remain STT-specific if it continues to describe the STT engine dependency set inside a broader voice plugin.

## Migration Decisions Required Before Implementation

1. Decide whether `plugin:stt|...` remains as a temporary compatibility namespace or the rename is a clean break.
2. Decide whether Rust compatibility aliases remain for `tauri_plugin_stt`, `TauriPluginSttExt`, and `tauri_plugin_stt()`.
3. Decide the TypeScript package name. The current name, `tauri-plugin-tauri-plugin-stt-api`, should be corrected during the rename.
4. Decide command naming for bootstrap and health: aggregate voice commands, engine-specific commands, or both.
5. Decide whether `download_model` gets an engine discriminator before TTS exists.
6. Decide whether model progress events add an `engine` field before adding TTS.
7. Decide whether recorder bridge commands remain under the voice plugin namespace or split back to recorder ownership in a later task.

## Recommended Rename Boundary

For readability and low migration risk, treat the rename as a public API migration with explicit compatibility decisions:

- Rename the package and primary plugin namespace to `tauri-plugin-voice` and `plugin:voice|...`.
- Keep STT-specific domain commands where they describe STT behavior, such as `transcribe_file`.
- Rename aggregate lifecycle commands only after the HLD chooses the voice-level readiness model.
- Add an engine discriminator to model download and progress contracts before TTS implementation.
- Update Steno only after the plugin migration strategy is approved.
